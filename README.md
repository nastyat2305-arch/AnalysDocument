# AnalysDocument
Практика 1 курс, Программа для анализа пищевых Гостов с эталонными документами (ТР ТС021 и МР2.3), команда Сыр

# 📄 GOST Analyzer AI — Анализатор нормативной документации


**Автоматизированная система анализа технической документации на базе гибридной RAG-архитектуры**

---

##  О проекте

GOST Analyzer AI — это интеллектуальная система для автоматического сравнения пользовательских технических документов (ГОСТ, ТУ, ТК, ТИ, ТТК, МУ) с эталонными нормативными актами (**ТР ТС 021/2011** «О безопасности пищевой продукции» и **МР 2.3.0279-22** «Рекомендации по производственному контролю»).

###  Решаемая проблема

При разработке технической документации производители должны обеспечить её соответствие требованиям технических регламентов Таможенного союза. Ручная проверка:
- ❌ Занимает много времени (часы на один документ)
- ❌ Требует экспертных знаний в области нормоконтроля
- ❌ Подвержена человеческим ошибкам
- ❌ Не масштабируется при больших объёмах документов

**Наше решение** автоматизирует этот процесс, находя три типа несоответствий:
1.  **Логические противоречия** — прямые конфликты числовых параметров, условий или требований
2.  **Смысловые разрывы** — отсутствие в документе обязательных положений, присутствующих в эталоне
3.  **Структурные различия** — нарушение ожидаемой композиции документа (отсутствие обязательных разделов)

## Архитектура системы

### Почему выбран именно такой подход?

Проект построен на **гибридной RAG-архитектуре** (Retrieval-Augmented Generation), которая сочетает быстрый векторный поиск с глубоким семантическим анализом через большие языковые модели (LLM).

####  Проблема «чистого» LLM-подхода

Полная загрузка документов в контекстное окно нейросети приводит к:
- Высокой стоимости и лимитам токенов
- Потере внимания модели на длинных текстах (lost-in-the-middle phenomenon)
- Медленной обработке больших массивов документов
- Невозможности работы с локальными моделями на слабом железе

####  Наше решение: двухуровневая фильтрация

[Документ] → [Векторизация] → [Поиск Top-K похожих блоков] → [AI-анализ] → [Отчёт]

1. **Эмбеддинги** (sentence-transformers) мгновенно отфильтровывают нерелевантные фрагменты
2. **LLM** анализирует только пары «Эталон ↔ Документ» с высокой косинусной схожестью
3. **Результат**: сокращение расхода токенов на ~80% и ускорение анализа в 5–10 раз

###  Модульная архитектура

Проект разделён на независимые модули с чёткой ответственностью:

| Модуль | Функция | Почему так? |
|--------|---------|-------------|
| `file_loader.py` | Загрузка `.txt` и `.docx`, определение типа документа | Единая точка входа для всех форматов |
| `text_splitter.py` | Разбивка на перекрывающиеся смысловые блоки (chunking) | Сохранение контекста при векторизации |
| `embedder.py` | Векторизация через sentence-transformers + кэширование | Синглтон для экономии памяти, кэш ускоряет повторные запуски |
| `comparator.py` | Поиск Top-K похожих блоков → отправка в LLM → парсинг JSON | Ядро RAG, контекстная фильтрация по продукту |
| `structure_analyzer.py` | Проверка наличия обязательных разделов через AI | Гибкая проверка без жёстких шаблонов |
| `report_generator.py` | Формирование отчётов (Console/JSON/TXT) | Разделение логики генерации и бизнес-логики |
| `main.py` | Оркестрация, CLI-меню, управление конфигурацией | Точка входа, координация модулей |

# Как работает анализ (пошагово)

## Этап 1: Подготовка эталонов ##
-Загрузка файлов из etalons/
-Разбивка на смысловые блоки (чанки) с перекрытием
-Векторизация через SentenceTransformer
-Сохранение векторов в ./cache/ (ускоряет повторные запуски)

## Этап 2: Анализ пользовательских документов ##
-Загрузка файлов из указанной папки (рекурсивно)
-Определение типа (ГОСТ, ТУ, ТК и т.д.) по имени и заголовку
-Извлечение контекста продукта (жиры, мясо, молоко и т.д.)
-Контекстная фильтрация эталонных блоков (оставляем только релевантные продукту)
-Векторный поиск: для каждого блока документа находятся Top-3 наиболее похожих блока эталона (порог схожести 0.35)
-AI-валидация: пары отправляются в LLM с промптом на поиск противоречий и разрывов
-Парсинг ответа: pydantic валидирует JSON, отсеивает malformed-ответы
-Структурная проверка: отдельный запрос к LLM проверяет наличие обязательных разделов

## Этап 3: Генерация отчёта ##
-Вывод в терминал с цветовой разметкой (rich)
-Сохранение в JSON/TXT по выбору пользователя
-Подсчёт статистики: всего документов, найдено противоречий, критических ошибок

#  Ключевые особенности 

## 1. Контекстно-зависимая фильтрация
Проблема: Сравнение узкоспециализированного ГОСТа (например, на жиры) с рамочным ТР ТС (на всю пищевую продукцию) генерирует много «шума» — система находит требования к другим продуктам (икра, детское питание, зерно).
### Решение:
Извлечение продуктового контекста из анализируемого файла (ключевые слова: «жир», «мясо», «молоко»)
Векторная фильтрация блоков эталона по семантической близости к контексту
Сравнение только релевантных блоков
### Результат: сокращение ложных срабатываний с ~130 до ~5-10 на документ.

## 2. Многопоточность с ограничением нагрузки
Параллельная обработка файлов (4 потока по умолчанию)
Semaphore(5) предотвращает превышение лимитов API
Оптимизация под I/O-bound задачи (запросы к сети/диску)

## 3. Кэширование векторов
Эмбеддинги эталонов сохраняются в ./cache/
При повторном запуске загрузка эталонов занимает <1 секунды
Экономия времени и ресурсов (не нужно векторизовать заново)

## 4. Структурированный вывод через Pydantic
Гарантированный формат ответа от LLM
Автоматическая валидация JSON
Избежание парсинга регулярками и ошибок

# ⚠️ Ограничения и особенности

##  Шум при сравнении разнородных документов
Программа сравнивает конкретный стандарт (например, ГОСТ на жиры) с рамочным регламентом (ТР ТС на всю пищевую продукцию). Часть найденных «разрывов» носит формальный характер — это требования к другим видам продукции.
### Рекомендация: 
Используйте отчёт как фильтр для приоритетной ручной проверки. Обращайте внимание на:
Числовые противоречия для одного продукта (критично!)
Отсутствие ссылок на техрегламенты
Нарушения структуры документа

##  Зависимость от качества эмбеддингов
Модель all-MiniLM-L6-v2 оптимизирована под скорость. Для повышения точности можно заменить на paraphrase-multilingual-mpnet-base-v2 (требует больше ОЗУ).

##  Идемпотентность
Повторные запуски используют кэш векторов, что снижает время подготовки эталонов до <1 сек.
